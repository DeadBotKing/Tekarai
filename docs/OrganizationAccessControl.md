# ساختار سازمانی و کنترل دسترسی (Organisation & Access Control)

> **خلاصه در یک جمله:** دسترسی از ترکیب **کاربر + واحد + سمت** ساخته می‌شود،
> هر دسترسی یک **محدوده** دارد، و افزودن واحد یا سمت جدید هیچ کدنویسی
> لازم ندارد.

---

## ۱. چرا نقش (Role) کافی نبود

در مدل قبلی، دسترسی به «نقش» گره خورده بود. مشکل این است که نقش، مکان را
نمی‌داند:

- «مدیر» در واحد فنی و مهندسی با «مدیر» در واحد تولید یک چیز نیست.
- «تکنسین» باید دستور کارهای **خودش** را ببیند، نه همه را.
- کارخانه فردا واحد «انبار» را اضافه می‌کند و نباید منتظر برنامه‌نویس بماند.

به همین دلیل واحد اصلی دسترسی در این سامانه **انتساب (Assignment)** است:

```
علی   + فنی و مهندسی + مدیر    →  یک principal
رضا   + فنی و مهندسی + تکنسین  →  principal کاملاً دیگری
علی   + تولید        + مدیر    →  باز هم متفاوت
```

یک کاربر می‌تواند چند انتساب داشته باشد (مثلاً «رئیس تعمیرات» که در زمان
توقف خط، «سرپرست برق» هم هست). در این حالت دسترسی‌ها **اجتماع** می‌شوند و
در تداخل، **وسیع‌ترین محدوده** برنده است.

---

## ۲. اجزای مدل

| جزء | چیست | کجا تعریف می‌شود |
|---|---|---|
| **واحد** (Department) | فنی و مهندسی، QC، QA، HSE، تولید، … | داده — از داخل برنامه |
| **سمت** (Position) | مدیر، رئیس، سرپرست، کارشناس، تکنسین، اپراتور، … | داده — از داخل برنامه |
| **انتساب** (Assignment) | کاربر + واحد + سمت | داده — از داخل برنامه |
| **قابلیت** (Capability) | دستور کار، تجهیزات، انبار، مجوز کار، … | کد — چون باید به کد مجوز واقعی وصل باشد |
| **عملیات** (Action) | View / Create / Edit / Delete / Approve / Assign / Close / Export | کد |
| **قاعده** (Access Rule) | سمت × قابلیت × عملیات → محدوده، به‌صورت اختیاری محدود به یک واحد | داده — ماتریس قابل ویرایش |

**چرا قابلیت و عملیات کد هستند و بقیه داده؟** چون هر خانهٔ ماتریس باید به یک
کد مجوز **واقعی** نگاشت شود که API آن را بررسی می‌کند. اگر مدیر سیستم بتواند
قابلیت دلخواه بسازد، تیکی خواهیم داشت که هیچ چیزی را کنترل نمی‌کند — و یک
صفحهٔ دسترسی که دروغ بگوید، از نبودنش بدتر است. به همین دلیل سرویس، خانه‌ای
را که در فهرست قابلیت‌ها نباشد **رد می‌کند**.

## ۳. محدوده‌ها (Scope)

هر دسترسی اعطاشده همیشه یک محدوده دارد:

| محدوده | معنی | مثال |
|---|---|---|
| `own` — خودش | فقط رکوردهای خودش | تکنسین فقط WO خودش را ویرایش می‌کند |
| `team` — تیم | خودش + افرادی که به او گزارش می‌دهند | سرپرست |
| `department` — واحد | کل واحدهایی که در آن‌ها انتساب دارد | رئیس |
| `all` — کل کارخانه | همهٔ واحدها | مدیر کارخانه |

ترتیب: `own < team < department < all`.

دو نکتهٔ مهم:

1. **محدودهٔ ناشناخته، دسترسی نمی‌دهد.** اگر در داده‌ای مقدار نامعتبری بنشیند،
   `scopeCovers` مقدار `False` برمی‌گرداند. یک غلط املایی در seed نباید به
   wildcard تبدیل شود.
2. **نبودِ دسترسی یعنی رد، نه «بدون فیلتر».** تابع `scopeFilterFor` برای
   کاربری که grant ندارد `denied=True` برمی‌گرداند. این تفاوت میان «چیزی
   نبین» و «همه چیز را ببین» است.

قابلیت‌هایی که ذاتاً محدوده‌پذیر نیستند (انبار قطعات، سفارش خرید، نگهداری
پیشگیرانه، ماتریس دسترسی) به‌اجبار روی `all` تنظیم می‌شوند — ذخیرهٔ محدودهٔ
باریک‌تر، وعده‌ای است که موتور دسترسی به آن عمل نمی‌کند.

## ۴. ماتریس

برای هر سمت، در هر واحد:

```
                 مدیر    رئیس    سرپرست   تکنسین
مشاهده WO        all     dept    team     own
ایجاد WO         all     dept    team     —
ویرایش WO        all     dept    team     own      ← «فقط WO خودش»
حذف WO           dept    —       —        —
تأیید WO         all     dept    —        —
تخصیص تکنسین     all     dept    team     —
بستن WO          all     dept    team     —
خروجی گرفتن      all     dept    —        —
```

این جدول فقط **مقدار اولیه** است. هر خانه از داخل برنامه قابل تغییر است.

**چرا «مدیر» پیش‌فرض `department` است و نه `all`؟** چون مدیرِ یک واحد، مدیرِ
همان واحد است. دیدِ کل کارخانه کار دیگری است — «مدیر کارخانه» — و مدیر
سیستم آن سمت را می‌سازد و آگاهانه `all` می‌دهد. اگر هر «مدیر» پیش‌فرض `all`
می‌گرفت، اولین کسی که این عنوان را بگیرد کل کارخانه را می‌خواند، و این دقیقاً
فروپاشی مفهوم «واحد» است که این طراحی برای جلوگیری از آن وجود دارد.

**قاعدهٔ واحدِ خاص:** اگر برای یک واحد خاص قاعده‌ای ثبت شود، آن قاعده
جایگزین پیش‌فرض کل سازمان می‌شود — **حتی اگر محدودتر باشد**. این عمدی است:
«در QC سرپرست فقط کار خودش را ببیند» باید قابل بیان باشد.

**ماتریس فقط اضافه می‌کند.** هیچ خانه‌ای «deny» نیست. تنها جای سلب دسترسی،
رکوردهای `UserPermission` با `effect="deny"` در بافت identity است؛ آن‌ها بر
همه چیز مقدم‌اند. دلیل: برای قطع فوری دسترسی یک نفر باید **یک جا** وجود
داشته باشد.

## ۵. مسیر یک تصمیم

```
actionPermission("maintenance.workorder.approve")
  → PermissionGateDjango.hasPermission
    → AccessRepositoryDjango.grantsOfUser
        ├─ grant های نقش و عضویت (identity)
        ├─ grant های ساختار سازمانی ← accessContract.grantsForUser  ★ جدید
        └─ grant های مستقیم کاربر (از جمله deny ها)
    → PermissionEvaluator.hasPermission   (deny برنده است، سپس allow)
```

پل در `AccessRepositoryDjango.organizationGrants` است و از طریق قرارداد
عمومی `apps.organization.application.services.accessContract` عبور می‌کند —
تنها سطحی که معماری برای ارتباط میان بافت‌ها مجاز می‌داند. اگر این بافت در
دسترس نباشد، تابع فهرست خالی برمی‌گرداند و ورود کاربران مثل قبل کار می‌کند؛
خطای واقعی لاگ می‌شود و هرگز به «allow» تفسیر نمی‌شود.

### ابطال فوری

هر تغییر ساختاری — انتساب، حذف انتساب، غیرفعال‌کردن واحد، ویرایش یک خانهٔ
ماتریس — نسخهٔ دسترسی کاربران متأثر را از طریق
`apps.identity.application.services.authorizationInvalidation` بالا می‌برد.
دسترسی لغوشده در همان درخواست بعدی از بین می‌رود، نه وقتی که TTL تمام شود.

## ۶. اعمال واقعی محدوده روی دستور کارها

محدوده تا وقتی روی کوئری واقعی اعمال نشود، فقط یک عدد در پایگاه داده است.
برای دستور کارها این اتصال برقرار است:

**۱. انتساب در زمان ثبت.** هر WO با سه شناسه مهر می‌شود:
`orgDepartmentId` (واحدِ مالکِ کار، از انتساب اصلیِ ثبت‌کننده)،
`requestedByUserId` و `assignedToUserId`. فیلدهای نامِ قبلی برای نمایش‌اند و
نمی‌توانند مبنای تصمیم دسترسی باشند — دو «رضا» در کارخانه یک نفر نیستند.

> `orgDepartmentId` عمداً از فیلد `department` قبلی جداست؛ آن یکی تیم
> اجرایی نت است (برق، مکانیک) و به پرسش دیگری پاسخ می‌دهد.

**۲. فیلتر در فهرست.** `WorkOrderListView` شناسهٔ کاربر را از نشست
می‌گیرد — نه از پارامتر — و محدوده **قبل از هر فیلتر دیگری** اعمال می‌شود.
هیچ query parameter ای نمی‌تواند آن را گشاد کند.

**۳. بررسی تک‌رکوردی.** `GET` و `PATCH` روی یک WO از همان resolve عبور
می‌کنند و در صورت خارج‌بودن، `403` می‌دهند. چون فهرست و جزئیات از یک منبع
می‌خوانند، کاربر هرگز سطری نمی‌بیند که بازکردنش رد شود.

**۴. تکنسین، کارِ واگذارشده را هم می‌بیند.** محدودهٔ `own` علاوه بر کارهایی
که خودش ثبت کرده، کارهایی را که به او ارجاع شده هم در بر می‌گیرد؛ در غیر
این صورت «کار خودش» شامل کاری که به او سپرده‌اند نمی‌شد.

**۵. سازگاری با گذشته.** اگر سازمانی هنوز واحدی تعریف نکرده باشد
(`hasOrganizationStructure` نادرست)، هیچ فیلتری اعمال نمی‌شود و همه چیز مثل
قبل کار می‌کند. اما اگر ساختار **تعریف شده باشد** و کاربر دسترسی نداشته
باشد، نتیجه خالی است نه کامل. این عدم‌تقارن عمدی است:
**نبودِ پیکربندی بازدارنده نیست، نبودِ مجوز هست.**

## ۷. فیلتر کردن سایر فهرست‌ها

دو تابع مکمل، هر دو از یک resolve:

```python
from apps.organization.application.services.accessContract import (
    scopeFilterForUser, userCanActOnRecord,
)

# برای کوئری فهرست
f = scopeFilterForUser(tenantId, userId, "maintenance.workorder.list")
if f.denied:
    return []
if not f.unrestricted:
    queryset = queryset.filter(assigneeId__in=f.userIds)   # یا departmentId__in

# برای یک رکورد مشخص
userCanActOnRecord(tenantId, userId, "maintenance.workorder.update",
                   ownerUserId=wo.assigneeId, departmentId=wo.departmentId)
```

چون هر دو از یک `AccessProfile` ساخته می‌شوند، کاربر هرگز سطری را در فهرست
نمی‌بیند که نتواند بازش کند.

## ۸. API

| متد | مسیر | مجوز |
|---|---|---|
| GET/POST | `/api/v1/organization/departments` | `organization.department.view` / `.manage` |
| GET/PATCH/DELETE | `/api/v1/organization/departments/{id}` | همان |
| GET/POST | `/api/v1/organization/positions` | `organization.position.view` / `.manage` |
| PATCH/DELETE | `/api/v1/organization/positions/{id}` | همان |
| GET/POST | `/api/v1/organization/assignments` | `organization.assignment.view` / `.manage` |
| PATCH/DELETE | `/api/v1/organization/assignments/{id}` | همان |
| GET/POST | `/api/v1/organization/access-matrix` | `organization.accessRule.view` / `.manage` |
| GET | `/api/v1/organization/my-access` | فقط ورود |
| GET | `/api/v1/organization/audit` | `organization.accessRule.view` |
| POST | `/api/v1/organization/seed` | `organization.department.manage` |

`/my-access` عمداً هیچ مجوزی نمی‌خواهد: هر کس باید بتواند ببیند چه دسترسی‌ای
دارد. ندانستنِ دلیلِ نبودن یک دکمه، همان چیزی است که به اشتراک‌گذاری رمز
منجر می‌شود.

خطاها: `400` خطای اعتبارسنجی، `422` ردِ قاعده با کد پایدار و پیام فارسی،
`404` نبودن رکورد.

## ۹. قواعدی که سامانه رد می‌کند

| کد | چرا |
|---|---|
| `department.cycle` / `department.selfParent` | حلقه در چارت، «کاربر در کدام واحد است؟» را بی‌پاسخ می‌کند |
| `department.hasMembers` / `.hasChildren` | حذف واحد، انتساب‌ها را یتیم و دسترسی را بی‌صدا قطع می‌کند |
| `department.systemProtected` / `position.systemProtected` | واحدها و سمت‌های پیش‌فرض فقط غیرفعال می‌شوند |
| `department.codeTaken` / `position.codeTaken` | کد، مرجع seed و import و یکپارچه‌سازی است |
| `assignment.duplicate` | یک سمت دوبار در یک واحد، خطای داده است |
| `assignment.departmentInactive` | «غیرفعال» باید واقعاً یعنی دسترسی قطع است |
| `assignment.selfReporting` | حلقه در زنجیرهٔ گزارش‌دهی، محدودهٔ `team` را خراب می‌کند |
| `rule.unsupportedCell` | تیکی که هیچ کدی آن را بررسی نمی‌کند، دروغ است |
