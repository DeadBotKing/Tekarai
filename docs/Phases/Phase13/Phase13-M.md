## 1. هدف و سؤال معماری

زیر‌فاز L سطح خطای پایدار و آداپتورها را تثبیت کرد؛ اما هر فراخوان هنوز
«یک شات» بود: یک تایم‌اوت یا یک 429 مستقیماً به مصرف‌کننده می‌رسید و هیچ
مسیر جایگزینی وجود نداشت. §25 سند مادر صریحاً Failover می‌خواهد:

> Primary Model → Failure → Secondary Model → Failure → Local Model — و این
> رفتار باید Configurable باشد.

M به این سؤال پاسخ می‌دهد:

> چگونه روی همان سطح خطای پایدارِ L، تلاش مجددِ کنترل‌شده، زنجیرهٔ جایگزینی
> پیکربندی‌محور، بودجهٔ زمانی کل عملیات و یک مرز خطای نهایی بسازیم — بدون
> هیچ وابستگی به فریم‌ورک، شبکه یا فروشنده، و کاملاً قابل تست آفلاین؟

اصول ثابت:

1. **هر خطایی قابل Retry نیست** (§44): فقط کلاس‌های «گذرا» دوباره تلاش
   می‌شوند؛ ورودی نامعتبر، مجوز و خطاهای ساختاری فوراً متوقف می‌شوند؛
2. **مرز خطا فقط خطای دامنه عبور می‌دهد** — هر چیز ناشناخته در مرز به خطای
   پایدار دامنه تبدیل می‌شود (fail-closed)؛
3. **Fallback پیکربندی‌محور است** (§25/§42) — هیچ زنجیره‌ای در کد هاردکد
   نمی‌شود؛
4. **ایدمپوتنسی دست نمی‌خورد** (§45): تلاش مجدد همان عملیات را با همان
   `idempotencyKey` تکرار می‌کند؛ ذخیره‌سازی و تضمین آن در P/Z باقی می‌ماند؛
5. همهٔ رفتارها با ساعت/خواب تزریقی، قطعی و آفلاین تست می‌شوند.

## 2. Scope و Non-Scope

### 2.1 داخل Scope

- `RetryPolicy` (frozen): تعداد تلاش، پشت‌هم‌اندازی نمایی با سقف، جدول
  اعتبارسنجی؛
- طبقه‌بندی خطا (`RetryClassifier`): کدام کدهای خطای دامنه «گذرا» هستند؛
- `FallbackPolicy`: زنجیرهٔ مرتب کدهای پرووایدر (اولی = اصلی) با نرمال‌سازی؛
- `ResilientProviderExecutor`: اجرای عملیات روی رجیستری فاز 13-D با تلاش
  مجدد، جایگزینی، بودجهٔ زمانی و گزارش تلاش‌ها؛
- مرز خطا (Error Boundary): هر استثنا غیردامنه‌ای به `AIProviderUnavailable`
  نگاشت و «مهلک» طبقه‌بندی می‌شود؛
- گزارش تلاش‌ها (`ResilienceReport`/`AttemptRecord`) + هوک ثبت برای
  مشاهده‌پذیری (مصرف‌کننده: N و W)؛
- قلاب بودجهٔ زمانی کل عملیات (جدا از تایم‌اوت هر فراخوان در ترنسپورت L)؛
- سیم‌کشی تنظیمات (`AI_RESILIENCE`) + متغیرهای محیطی؛
- متد 편의 `generateWithFallback` روی `GenerationRequest` فاز 13-C؛
- تست واحد قطعی (ساعت/خواب جعلی) + تست یکپارچگی با سرور محلی «اتفاقی‌ساز»
  (خطا-بعد-موفقیت) روی سوکت واقعی.

### 2.2 خارج از Scope

- شمارش مصرف/هزینه و سهمیه — زیر‌فاز **N**؛
- Audit فراخوانی‌ها — زیر‌فاز **O**؛
- اجرای Async/صف/ورکر — زیر‌فاز **P**؛
- مدار قطع (Circuit Breaker) — اگر لازم شود با تصمیم جدید در زیر‌فاز مستقل؛
- تغییر آداپتورها یا قرارداد پورت — بدون هیچ تغییری در سطح L.

## 3. جایگاه معماری

```text
Application (استفاده‌کننده: سرویس‌های قابلیت)
        │
        ▼
Phase 13-M ResilientProviderExecutor  ← این زیر‌فاز
   ├── تلاش مجدد با پشت‌هم‌اندازی (طبقه‌بندی خطا)
   ├── زنجیرهٔ جایگزینی پیکربندی‌محور
   ├── بودجهٔ زمانی عملیات
   └── مرز خطا + گزارش تلاش‌ها
        │
        ▼
Phase 13-D ProviderRegistry  ← resolve(tenantId, providerCode)
        │
        ▼
Phase 13-L Adapterها (بدون تغییر) ← خطاهای پایدار دامنه
```

قواعد:

1. اجراکننده یک سرویس دامنهٔ خالص است؛ فقط رجیستری، پورت و خطاهای دامنه را
   می‌شناسد؛ نه Django، نه شبکه، نه فروشنده؛
2. ساعت و خواب از طریق پورت تزریق می‌شوند — پیش‌فرض‌های واقعی فقط برای
   اجرا؛ تست‌ها نمونهٔ جعلی و قطعی می‌دهند؛
3. مصرف‌کننده نتیجهٔ موفق را از `ExecutionOutcome` می‌گیرد و در شکست، همان
   خطای دامنهٔ پایدار را — با گزارش پیوست‌شده برای مشاهده‌پذیری.

## 4. قراردادهای داده

### 4.1 `RetryPolicy`

| فیلد | قاعده |
|---|---|
| `maxAttempts` | عدد صحیح ≥ ۱ (تعداد کل تلاش‌ها برای هر گام زنجیره) |
| `initialBackoffSeconds` | ≥ ۰ |
| `backoffMultiplier` | ≥ ۱ |
| `maxBackoffSeconds` | ≥ پشت‌هم‌اندازی اولیه (سقف) |
| `retryableErrorCodes` | مجموعهٔ کدهای پایدار؛ پیش‌فرض طبق §5 |

پشت‌هم‌اندازی تلاش `n` (شروع از صفر): `min(initial × multiplier^n, max)` —
قطعی و بدون لرزش (jitter در زیر‌فاز مستقل و در صورت نیاز واقعی).

### 4.2 طبقه‌بندی خطا (نهایی — مطابق §44 سند مادر)

| کد خطا | طبقه | رفتار |
|---|---|---|
| `AI_REQUEST_TIMEOUT` | گذرا | تلاش مجدد |
| `AI_PROVIDER_UNAVAILABLE` | گذرا | تلاش مجدد |
| `AI_PROVIDER_RATE_LIMITED` | گذرا | تلاش مجدد |
| `AI_MODEL_UNAVAILABLE` | مهلک | توقف (مدل جایگزین از طریق تنظیم زنجیره، نه تلاش مجدد) |
| `AI_OUTPUT_VALIDATION_FAILED` | مهلک | توقف |
| `SYS_VALIDATION_FAILED` (ورودی نامعتبر) | مهلک | توقف |
| `AI_PERMISSION_DENIED` / سایر مجوزها | مهلک | توقف |
| `AI_QUOTA_EXCEEDED` | مهلک | توقف |
| هر استثنا غیردامنه‌ای | مهلک | در مرز به `AIProviderUnavailable` نگاشت می‌شود |

### 4.3 `FallbackPolicy`

- tuple مرتب از کدهای پرووایدر؛ عضو اول = اصلی؛
- نرمال‌سازی به حروف بزرگ؛ تکراری رد می‌شود؛
- زنجیرهٔ خالی مجاز است یعنی «بدون جایگزینی».

### 4.4 گزارش تلاش‌ها

`AttemptRecord` (frozen): `providerCode`، `attemptNumber`، `outcome`
(`SUCCESS` / `RETRYABLE_ERROR` / `FATAL_ERROR` / `SKIPPED`)، `errorCode`،
`backoffSeconds`.

`ResilienceReport` (frozen): `success`، `finalProviderCode`، `attempts`،
`fallbackUsed`، `finalErrorCode`، `totalBackoffSeconds` + `attemptsCount`.

در شکست نهایی، گزارش روی همان استثنا پیوست می‌شود
(`resilienceReport`) تا لایه‌های بالاتر بدون تغییر امضا به آن برسند؛
دستیار `reportFromError()` خواندن امن آن است.

### 4.5 پورت‌های زمان

`ResilienceClock.monotonicSeconds()` و `ResilienceSleeper.sleep(seconds)` —
پروتکل‌های کوچک برای تزریق؛ پیش‌فرض‌ها `MonotonicClock` و `RealSleeper`.

## 5. رفتار اجراکننده (الگوریتم مرجع)

```
گام‌ها = [اصلی] + جایگزین‌ها (بدون تکرار)
برای هر گام:
    اگر گام حل‌نشدنی است (ثبت‌نشده/غیرفعال) و گامِ اصلی نیست → ثبت SKIPPED، ادامه
    برای تلاش ۱..maxAttempts:
        اگر بودجهٔ زمانی تمام شده → خطای تایم‌اوت عملیات + گزارش
        اجرا در مرز خطا:
            موفق → بازگشت نتیجه + گزارش موفق
            مهلک → پرتاب همان خطا + گزارش (بدون تلاش مجدد، بدون جایگزینی)
            گذرا → ثبت تلاش؛ اگر تلاش باقی است خواب(پشت‌هم‌اندازی)
    → ادامه به گام بعدی زنجیره
پایان زنجیره → پرتاب آخرین خطای گذرا + گزارش
```

نکات رفتاری:

- حل‌نشدن گام **اصلی** (ثبت‌نشده/غیرفعال) همان‌جا پرتاب می‌شود — خطای
  پیکربندی است و جایگزینی معنایی ندارد؛
- بودجهٔ زمانی با ساعت تزریقی سنجیده می‌شود و کل زنجیره را پوشش می‌دهد؛
- هوک ثبت (`recorder`) برای هر رکورد تلاش فراخوانی می‌شود — مصرف‌کنندهٔ
  مشاهده‌پذیری/ممیزی در N و W.

## 6. پیکربندی (متغیرهای محیطی — §42)

| متغیر | پیش‌فرض | معنا |
|---|---|---|
| `aiRetryMaxAttempts` | 3 | تعداد تلاش برای هر گام |
| `aiRetryInitialBackoffSeconds` | 0.25 | پشت‌هم‌اندازی اولیه |
| `aiRetryBackoffMultiplier` | 2.0 | ضریب نمایی |
| `aiRetryMaxBackoffSeconds` | 5.0 | سقف پشت‌هم‌اندازی |
| `aiProviderTimeoutBudgetSeconds` | 60 | بودجهٔ زمانی کل عملیات |
| `aiProviderFallbackChain` | (خالی) | فهرست جداشده با کاما از کدهای پرووایدر |

بلوک `AI_RESILIENCE` در تنظیمات پایه ساخته می‌شود و سیم‌کشی
(`resilienceWiring`) از روی آن سیاست‌ها و اجراکننده را می‌سازد.

## 7. تست و تأیید

1. **واحد (قطعی، آفلاین):** اعتبارسنجی سیاست‌ها، جدول طبقه‌بندی، موفقیت در
   تلاش اول/سوم، توقف خطای مهلک، سقف تلاش، زنجیرهٔ جایگزینی دو و سه‌گامی،
   گام حل‌نشدنی (SKIPPED)، بودجهٔ زمانی با ساعت جعلی، هوک ثبت، مرز خطا،
   متد 편의 با پرووایدر قطعی، سیم‌کشی از تنظیمات؛
2. **یکپارچگی (سوکت واقعی):** سرور محلی «اتفاقی‌ساز» — ابتدا 503/429 و سپس
   200؛ شمارش درخواست‌های سمت سرور اثبات می‌کند تلاشها واقعاً تکرار شده‌اند؛
   مسیر مهلک (400) دقیقاً یک درخواست می‌فرستد؛
3. هیچ فراخوانی شبکه‌ای خارج از `127.0.0.1` انجام نمی‌شود؛
4. دروازهٔ کامل: تست سراسری، `manage.py check`، lint، تایپ،
   `makemigrations --check`.
