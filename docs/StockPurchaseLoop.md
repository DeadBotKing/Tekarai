# حلقه انبار → خرید (Stock→Purchase Loop)

## مسئله‌ای که حل شد

هر سه قطعهٔ این زنجیره از قبل وجود داشت و هیچ‌کدام به هم وصل نبود:

| چیزی که وجود داشت | جایش |
|---|---|
| تشخیص «موجودی زیر حداقل» | `SparePart.lowStock` + رویداد `sparePartLowStock` |
| اینکه چه کسی این قطعه را می‌فروشد، به چه قیمت، با چه مهلت و حداقل سفارش | `SupplierPartModel` (`unitPrice`, `leadTimeDays`, `isPreferred`, `minimumOrderQty`) |
| زنجیرهٔ خرید | درخواست → تأیید → سفارش → رسید → فاکتور |

نتیجه این بود که هشدار کمبود موجودی فقط یک اعلان بود؛ یک نفر باید آن را می‌دید، می‌رفت
سراغ کاتالوگ تأمین‌کننده، و عددهایی را که سیستم همین حالا داشت دوباره دستی وارد می‌کرد.

این حلقه آن وصل‌نشدگی را می‌بندد:

```
موجودی زیر حداقل  →  پیشنهاد خرید  →  درخواست خرید پیش‌نویس
                                          ↓
                          (زنجیرهٔ موجود: تأیید → سفارش → رسید)
```

---

## سه قاعده‌ای که کل طراحی روی آن‌ها ایستاده

### ۱) کالای در راه هم موجودی است

نقطهٔ تصمیم **موجودی خالص** است، نه آنچه روی قفسه است:

```
موجودی خالص = موجودی انبار + سفارش‌های باز
```

«سفارش‌های باز» یعنی هر دوی این‌ها:

* سطرهای درخواست‌های خرید در وضعیت `draft`/`submitted`/`approved`/`ordered`
* **مانده‌ی تحویل‌نشدهٔ** سفارش‌های خرید (`orderedQuantity − receivedQuantity`)

اگر این را حساب نکنی، یک کرون روزانه هر شب دوباره برای همان قطعه درخواست می‌سازد تا
وقتی کالا برسد. این دقیقاً همان مسیری است که چنین قابلیتی تبدیل به تولیدکنندهٔ اسپم
می‌شود و کاربر خاموشش می‌کند.

مهم‌تر: چون پیش‌نویسی که همین اسکن می‌سازد بلافاصله «در راه» حساب می‌شود،
**اجرای دوبارهٔ اسکن هیچ چیزی پیشنهاد نمی‌دهد**. idempotency اینجا از حسابِ ریاضی
می‌آید، نه از یک کلید deduplication که باید جداگانه نگه‌داری شود.

### ۲) سفارش تا سطح هدف، نه فقط به اندازهٔ کسری

```
سطح هدف  = حداقل موجودی + مقدار سفارش (reorderQuantity)
مقدار    = سطح هدف − موجودی خالص
```

اگر فقط کسری را سفارش بدهی، قطعه دقیقاً روی نقطهٔ سفارش می‌نشیند و اولین مصرف
بعدی دوباره هشدار را فعال می‌کند.

### ۳) آنچه تأمین‌کننده واقعاً می‌فروشد

نیاز محاسبه‌شدهٔ ۳ عدد وقتی `minimumOrderQty` تأمین‌کننده ۱۰ است، سفارشی نیست که
کسی بتواند ثبت کند. مقدار تا حداقل سفارش بالا برده می‌شود.

## پیکربندی

دو فیلد جدید روی قطعهٔ انبار:

| فیلد | پیش‌فرض | معنی |
|---|---|---|
| `reorderQuantity` | `0` | چقدر بخریم. **صفر یعنی تنظیم‌نشده** — سیاست به «پر کردن تا دو برابر حداقل» برمی‌گردد |
| `autoReorder` | `true` | خاموش کردن برای قطعه‌هایی که نباید خودکار پیشنهاد شوند (موجودی در حال اتمام عمدی، اقلام پروژه‌ای، کالای امانی) |

**حلقه بدون هیچ پیکربندی‌ای کار می‌کند.** این عمدی است: اگر `reorderQuantity` اجباری
بود، این قابلیت تا وقتی کسی تک‌تک قطعه‌ها را ویرایش نکند هیچ کاری نمی‌کرد.

قطعه‌ای که `autoReorder` آن خاموش است **حذف نمی‌شود** — در فهرست `skipped` با دلیلش
می‌آید. حذف بی‌صدا از نگاه کاربر با «اسکن اصلاً این قطعه را ندید» فرقی ندارد.

## فوریت

| موجودی خالص | فوریت | مهلت معطلی درخواست |
|---|---|---|
| ≤ ۰ | `critical` | ۲ روز |
| ≤ نصف حداقل | `high` | ۴ روز |
| بقیه | `normal` | ۷ روز |

این مقادیر عمداً همان واژگان اولویت درخواست خرید هستند، پس درخواستی که از کمبود
بحرانی ساخته شده، خودش هم زودتر پیگیری می‌شود — بدون اینکه هیچ‌کدام از دو قابلیت
از وجود دیگری خبر داشته باشد. درخواستی که چند قلم دارد، **فوری‌ترین** اولویت را
به ارث می‌برد تا یک قلم روتین، یک توقف خط تولید را کند نکند.

## استفاده

### رابط کاربری

تدارکات و خرید ← تب **«تأمین انبار»**. جدول موجودی، حداقل، در راه، خالص، پیشنهاد،
تأمین‌کننده و برآورد مبلغ را نشان می‌دهد؛ حساب‌وکتاب روی صفحه است تا عدد قابل‌بازرسی
باشد، نه چیزی که یک ربات ادعا کرده. دکمهٔ «ساخت درخواست‌های خرید» پشت مجوز
`procurement.requisition.create` است.

### API

```
GET  /api/v1/procurement/replenishment    # پیش‌نمایش، چیزی نمی‌نویسد
POST /api/v1/procurement/replenishment    # ساخت پیش‌نویس‌ها
```

مجوزها: `GET` → `procurement.supplier.view`؛ `POST` → `procurement.requisition.create`.
مجوز جدیدی تعریف نشد — این مسیر دقیقاً همان شیئی را می‌سازد که آن مجوز از قبل
محافظت می‌کند، پس هیچ نقشی بی‌سروصدا اجازهٔ تعهد هزینه پیدا نمی‌کند.

### خط فرمان

```bash
python manage.py runReplenishment                    # پیش‌نمایش (پیش‌فرض)
python manage.py runReplenishment --apply            # ساخت پیش‌نویس‌ها
python manage.py runReplenishment --tenant <uuid> --apply
```

**پیش‌نمایش پیش‌فرض است.** نوشتن اسناد خرید کاری نیست که یک خط کرون به‌خاطر یک
اشتباه تایپی شروع به انجامش کند؛ `--apply` انتخاب صریح است.

```cron
# هر روز ساعت ۰۶:۰۰
0 6 * * * cd /srv/tekarai/backend && .venv/bin/python manage.py runReplenishment --apply
```

```powershell
schtasks /create /tn "Tekarai Replenishment" /sc daily /st 06:00 `
  /tr "`"C:\tekarai\backend\.venv\Scripts\python.exe`" C:\tekarai\backend\manage.py runReplenishment --apply"
```

اجرای روزانه امن است — قاعدهٔ «کالای در راه» تضمین می‌کند اجرای دوم چیزی اضافه نکند.

## تصمیم‌های طراحی و دلیلشان

**پیش‌نویس، نه درخواست ثبت‌شده.** ماشین می‌تواند نیاز را تشخیص دهد؛ تصمیمِ خرج کردن
پول هنوز با آدم است و زنجیرهٔ تأیید از همان‌جایی شروع می‌شود که همیشه می‌شد. ضمناً
ساعتِ معطلی از `submittedAt` شروع می‌شود، پس درخواست‌های تولیدشده قبل از اینکه
انسانی ببیندشان در فهرست «معطل‌مانده»ی خریدار ظاهر نمی‌شوند.

**یک درخواست به ازای هر تأمین‌کننده، نه هر قطعه.** ده قطعه از یک تأمین‌کننده یک
مکالمه و یک سفارش خرید است، نه ده تا. قطعه‌های بدون تأمین‌کننده در یک درخواست
بی‌تأمین‌کننده جمع می‌شوند تا دیده شوند.

**انتخاب تأمین‌کننده:** تأمین‌کنندهٔ `isPreferred` برنده است؛ در نبودش ارزان‌ترین
قیمت، و در تساوی قیمت، کوتاه‌ترین `leadTimeDays`. خریدار همیشه می‌تواند روی
پیش‌نویس عوضش کند.

**پنل UI عمداً fixture ندارد.** قانون مرز حالت دمو اجازه نمی‌دهد فایل جدیدی روی
آن پرچم شاخه بزند، چون هر شاخه یک پیادهٔ دوم است که از نسخهٔ واقعی فاصله می‌گیرد.
پنل یک مسیر کد دارد — API — و زیر fixture‌های دمو حالت خطا نشان می‌دهد نه فهرست
کمبود ساختگی.
