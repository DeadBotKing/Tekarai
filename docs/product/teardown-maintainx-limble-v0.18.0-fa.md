# Teardown ساختاریافتهٔ MaintainX + Limble، با الگوی میدانی UpKeep

## نقشهٔ راه درخواستی: `v0.18.0 — پاساژ زیباسازی UI`

**بازبینی:** ۲۱ اکتبر ۲۰۲۶

**مبنای مقایسه:** سورس فعلی Tekarai در `/home/user/Tekarai`، با تمرکز بر CMMS، درخواست/دستورکار، دارایی و استفادهٔ تکنسین.

**نسخهٔ موجود در سورس:** `frontend-web/package.json` برابر `0.19.0` است. برچسب `v0.18.0` در این سند همان نام roadmap درخواستی است؛ آن را به‌عنوان دستور عقب‌بردن نسخهٔ برنامه برداشت نکنید.

**دامنهٔ این سند:** teardown و backlog است؛ قابلیت‌های جدید Kanban، گفت‌وگوی پایدار و زمان‌بندی drag-and-drop در این پاس پیاده‌سازی نشده‌اند.

> **اصل طراحی:** از الگو و گردش‌کار الهام بگیریم، نه از پیکسل‌ها، رنگ‌ها یا چیدمان LTR. رنگ، اجزای پایه، RTL و تایپوگرافی Tekarai حفظ شود. هر الگو جداگانه و مرحله‌ای بررسی شود؛ مخلوط‌کردن پنج سبک در یک صفحه ممنوع.

## خلاصهٔ اجرایی

Tekarai همین حالا فهرست و برد درخواست‌های کار، جزئیات بخش‌بندی‌شده، تاریخچهٔ رویداد، تقویم PM، اسکن QR، آفلاین، پروفایل تجهیز و داشبورد نگهداری دارد. بنابراین پیشنهاد این سند «ساخت دوبارهٔ همه‌چیز» نیست؛ هدف این است که تکنسین زودتر ببیند چه کاری در انتظار اوست و مدیر بتواند وضعیت را بدون خروج از زمینهٔ کار پیگیری کند.

چهار شکاف اصلی نسبت به الگوهای درخواستی شما:

1. در جزئیات دستورکار، **رویدادهای سیستمی** به‌شکل تایم‌لاین واقعی نمایش داده می‌شوند؛ اما رشتهٔ نظر/گفت‌وگوی پایدار با عکس و پاسخ کاربر در مدل/API فعلی پیدا نشد. پیام محلی یا ساختگی نباید ساخته شود.
2. برد Kanban در `WorkOrdersPage.tsx` وجود دارد و ستون‌های وضعیت دارد، اما جابه‌جایی کارت با drag-and-drop پیاده‌سازی نشده است.
3. تقویم PM در `MaintenancePmCalendarPage.tsx` ماهانه است و بازکردن هر روز را پشتیبانی می‌کند؛ جابه‌جایی رخداد PM با کشیدن کارت وجود ندارد.
4. QR، ثبت دستورکار، آفلاین و گزارش‌های روزانه در بخش‌های مختلف موجودند، اما **صفحهٔ واحد «کارهای امروزِ تکنسین»** که این‌ها را کنار هم بگذارد، در مسیریابی/صفحهٔ فعلی پیدا نشد.

### کارهایی که در نسخهٔ فعلی قبلاً انجام شده‌اند

در پاس UI نسخهٔ `0.19.0`، کارت‌های داشبورد نگهداری پرداخت شده‌اند، برد موجود و کارت‌هایش خواناتر شده‌اند، جزئیات دستورکار بخش‌بندی و تاریخچهٔ واقعی مرتب‌تر شده، تب اسناد در پروفایل تجهیز اضافه شده و راهنمای زمینه‌ای سایت در دسترس است. این موارد را در roadmap جدید «کار جدید» حساب نکنید؛ فقط اگر آزمون RTL/کاربر مشکل نشان داد، برای آن‌ها polish محدود باز کنید. **بازطراحی کامل کارت داشبورد تکرار نشود.**

### ترتیب تحویل پیشنهادی: یک الگو در هر مرحله

1. **مرحلهٔ ۱ — friction کم‌خطر:** حالت‌های خالی فیلتر/فهرست و خانهٔ تکنسین با اتصال به قابلیت‌های موجود.
2. **مرحلهٔ ۲ — Work Order Activity:** API comment/attachment و سپس UI گفت‌وگوی پایدار. اگر API تأیید نشد، مرحله متوقف می‌ماند.
3. **مرحلهٔ ۳ — Kanban interaction:** فقط پس از تثبیت انتقال وضعیت، مجوزها، خطا و undo.
4. **مرحلهٔ ۴ — PM rescheduling:** فقط جابه‌جایی occurrence موجود؛ recurrence rule در فرم مجزا.
5. **مرحلهٔ ۵ — polish sweep:** RTL/LTR، long text، جدول‌ها، تقویم و dashboard micro-polish.

## ۴. RTL، فارسی و کیفیت مرجع‌گیری

- صفحات رقبا عمدتاً LTR و انگلیسی‌اند؛ grid/کارت را کپی نکنید. از CSS logical properties مثل `margin-inline`, `inset-inline` و `text-align: start` استفاده کنید.
- فونت فارسی Tekarai در سورس **Vazirmatn Variable** است و به‌شکل محلی bundle شده؛ آن را با IranSans جایگزین نکنید مگر design decision جداگانه و مجوز فونت داشته باشید.
- ارقام UI که باید فارسی باشند از formatter محلی استفاده کنند؛ شناسه، کد تجهیز، سریال و مقادیر قابل‌کپی/اسکن بی‌دلیل به رقم فارسی تبدیل نشوند.
- رشته‌های ترجمه‌شدهٔ فارسی غالباً از انگلیسی بلندترند: status label، نام واحد، متن کارت، toast، tooltip، عنوان modal و دکمهٔ دوکلمه‌ای با متن واقعی تست شوند.
- برای بررسی اپ‌های واقعی، **Mobbin را به Dribbble ترجیح دهید**؛ Dribbble فقط mood board است، نه منبع رفتار واقعی. منبع حقیقت، مسیرهای کاری و نسخه/plan واقعی MaintainX، Limble و UpKeep است؛ از screenshot کانسپت، قابلیت کسب‌وکاری نتیجه‌گیری نکنید.
- Drag-and-drop باید معادل دسترس‌پذیر (منوی انتخاب status/date، صفحه‌کلید، focus و announcement) داشته باشد؛ رنگ به‌تنهایی وضعیت را منتقل نکند.

## ۵. مرزهای محصول و موارد خارج از زیباسازی

- **کامنت ساختگی/محلی نداشته باشیم.** Chat عمومی جایگزین thread ثبت‌پذیر در درخواست نیست.
- **تعمیر اساسی از مصرفی جداست.** تغییر طبقه‌بندی یا مسیر تأیید در این roadmap نیست؛ شدت تعمیر نیاز به تأیید انسان دارد و پیشنهاد AI advisory می‌ماند.
- **Drag کردن، تصمیم کسب‌وکاری را پنهان نکند.** Kanban فقط انتقال status مجاز و PM فقط جابه‌جایی همان رخداد است؛ تغییر قانون تکرار، تأیید/رد، لغو یا هزینه باید control واضح خودش را داشته باشد.
- پورتال عمومی درخواست‌دهنده، ذخیرهٔ comment/notification، OCR/خواندن PDF و ظرفیت‌سنجی تیمی پروژه‌های قابلیت/زیرساخت جدا هستند؛ بدون API و معیار دسترسی به‌عنوان UI-only نمایش داده نشوند.
- نسخهٔ موجود `0.19.0` است؛ سند roadmap درخواستی `0.18.0` را حفظ می‌کند، اما تغییر `package.json` یا tag به نسخهٔ پایین‌تر لازم نیست.

## ۶. برنامهٔ آزمون برای اجرای roadmap

این teardown به‌تنهایی تغییر رفتار UI ایجاد نمی‌کند؛ بنابراین قابلیت‌هایی که هنوز پیاده‌سازی نشده‌اند نباید «تست‌شده» معرفی شوند. هنگام اجرای هر مرحله:

- **Build و regression:** `npm run build`، تست‌های مربوط به `sidenav`, `localization`, `workOrderEscalation`, `repairScopeSuggestion`, Kanban و PM calendar؛ سپس `npm run verify:demo-boundary`.
- **ماتریس مرور دستی:** فارسی RTL و انگلیسی LTR در ۳۲۰/۳۶۰/۳۹۰/۷۶۸/۱۲۸۰ پیکسل؛ mobile/desktop، صفحه‌کلید، اسکرین‌ریدر، متن بلند، دو رقم/کد تجهیز، empty/error/loading/offline.
- **Activity:** ذخیرهٔ واقعی comment، upload عکس، refresh/reopen، permission denial، دو کاربر، order رویدادها و خطای شبکه.
- **Kanban:** drop مجاز/غیرمجاز، انتقال به pending approval، conflict همزمان، رد backend، rollback، focus و تغییر با صفحه‌کلید.
- **PM calendar:** جابه‌جایی یک occurrence، لغو، محدودیت تعطیلات/تداخل، audit، undo و اطمینان از ثابت‌ماندن recurrence rule.
- **Technician home:** فقط کارهای مجاز کاربر، QR اسکن واقعی، دسترسی سریع به ثبت، نمایش offline queue و ادامهٔ timer واقعی؛ هیچ دادهٔ نمایشی به‌عنوان production معرفی نشود.

## ۸. نتیجهٔ اعتبارسنجی این پاس

- `npm run build`: موفق؛ TypeScript و Vite هر دو سبز شدند.
- آزمون‌های هدفمند: **۶ فایل، ۴۳ تست موفق** (`localization`, `sidenav`, `workOrderEscalation`, `repairScopeSuggestion`, `equipmentRegistry`, `demoModeBoundary`). چند هشدار React `act(...)` در تست سایدبار ثبت شد، اما تستی شکست نخورد.
- `npm run verify:demo-boundary`: موفق؛ ۷۰ artifact بررسی شد و رکورد ساختگی در build پیدا نشد.
- `git diff --check` و بررسی whitespace/ارجاع‌های همین سند: بدون خطا.
- هشدار غیرمسدودکنندهٔ build: یک bundle از ۵۰۰ kB بیشتر است؛ در scope این teardown اصلاح نشد.
- کل test suite در این پاس اجرا نشده است. تغییرات محصولی پیشنهادی این سند نیز پیاده‌سازی نشده‌اند؛ بنابراین آزمون DnD، comment API و خانهٔ تکنسین باید پس از توسعه و در scope مستقل اجرا شوند.
